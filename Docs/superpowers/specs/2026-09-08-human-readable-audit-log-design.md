# Human-Readable Audit Log Design

## Goal

Make the global Access Control Audit Log understandable to business administrators without removing the structured JSON evidence needed by technical investigators. A user must be able to understand the action and the important state transition from the table row and expanded summary; raw action codes, identifiers, policy versions, trace references, and sanitized JSON remain available as evidence.

## Confirmed decisions

- Every known audit action uses an explicit English, Malay, and Simplified Chinese summary. Summaries are not generated by splitting the action code.
- The human-readable summary is the primary text in the table's **Action** column. The immutable action code remains visible below it in monospace text.
- Expanded details show a human-readable key-change summary before the technical JSON.
- The before/after JSON remains available but is collapsed by default under a clearly labelled technical-details control.
- An unmapped future or legacy action displays the translated label **Unknown audit action** and still shows its original action code. It must never receive a guessed or potentially misleading translation.
- Existing privacy sanitization remains authoritative. The UI formats only the already-sanitized API payload and must not expose KYC documents, identity details, storage paths, internal notes, customer messages, credentials, or other removed fields.
- This change is frontend-only. It does not change audit records, append-only guarantees, API response shapes, Supabase tables, RLS, migrations, or retention behavior.

## Considered approaches

### 1. Exact action catalogue — selected

Maintain a typed catalogue from exact action code to an i18n summary key. This produces deliberate, grammatically correct wording in every supported language and makes missing coverage visible in tests. It requires a translation update whenever a new audit action is introduced.

### 2. Automatic action-code humanization — rejected

Splitting `domain.verb` strings would cover future actions with less maintenance, but it produces awkward translations and can misstate domain-specific operations. This conflicts with the audit log's evidentiary purpose.

### 3. Server-generated localized summaries — rejected

Generating summaries in the API could centralize the vocabulary, but it would couple the API to UI locale and duplicate presentation concerns in a security-focused JSON endpoint. The action code and sanitized structured data are the stable server contract; localization belongs in the client.

## Information hierarchy

### Table row

The existing seven-column table remains unchanged. The Action cell changes from a code-first presentation to:

1. Localized business summary in the primary text style.
2. Original action code in smaller monospace secondary text.
3. Existing sanitized reason text, when available.

For example:

```text
批准了 KYC 申请
kyc.approve
```

The actor, target, policy version, trace reference, timestamp, and Details control retain their current locations. This avoids widening the table or changing its filtering and navigation model.

### Expanded details

The expanded row contains two levels:

1. **Key changes** — a compact list of sanitized primitive fields whose before and after values differ. For the KYC approval event this reads `状态: 待审核 → 已批准`. Missing values use the existing none marker. Known status values and known field names use explicit i18n labels; an unrecognized sanitized field keeps its exact field key rather than receiving a guessed translation.
2. **Technical details** — a native accessible disclosure control, collapsed by default, containing the existing side-by-side Before and After JSON cards. Opening it does not fetch more data.

If no comparable before/after values exist, the key-change area displays a translated **No summarized field changes** message; the technical evidence remains available.

## Action catalogue

The catalogue is a small presentation module keyed by the exact immutable `action` string. It covers every action currently recognized by this repository's Audit Log UI and every action observed in the connected project's existing audit data during design. Initial required mappings include:

- `kyc.approve`, `kyc.reject`, `kyc.request_info`, `kyc.document_viewed`
- `recommendation.approve`, `recommendation.reject`, `recommendation.request_changes`
- `withdrawal.approve`, `withdrawal.reject`, `withdrawal.hold`, `withdrawal.resume`
- `affiliate.link.disabled`
- `tier.admin_set`
- Access Control actions under `entitlement.*`
- Staff role and assignment actions under `staff.*`
- Vendor approval, suspension, and recommendation-link actions emitted into `audit_logs`

Before implementation, repository search determines the final exact set. The implementation plan must list the mapped action codes. A test must fail if a catalogue entry lacks any of the three locale strings.

Unknown codes use one explicit fallback translation key. The original code is always rendered, so investigators can still search and correlate it.

## Key-change formatting

- Compare only values present in the sanitized `before` and `after` objects.
- Include a field when the two sanitized values are not deeply equal.
- Render strings, booleans, numbers, and null directly through safe formatters.
- Render known enum values, starting with audit statuses, through exact translation keys.
- Do not infer or display fields that the API omitted.
- Do not rehydrate sensitive details from another source in the client.
- Arrays and nested objects remain in technical JSON unless a later separately approved design adds a safe domain formatter.

## Component boundaries

- A presentation module owns the exact action-to-i18n mapping, safe field labels, enum labels, and change-row derivation. It has no network or React dependency.
- `AuditLogTab` continues to own fetching, filters, pagination, expansion state, and target navigation.
- `AuditRow` renders the localized action summary and original action code.
- A focused change-summary component renders the human-readable differences.
- The existing JSON payload component remains the technical evidence renderer inside the collapsed disclosure.

These boundaries keep business vocabulary independently testable and avoid adding more responsibilities to the already dense table component.

## Accessibility and localization

- Use the existing design tokens and button/card styles; do not introduce a new visual system.
- The technical-details disclosure must be keyboard operable and expose localized open/closed text.
- Do not communicate a state transition by color alone; both values remain visible as text.
- Add matching keys to `en`, `ms`, and `zh-CN` admin locale files.
- Dates continue to use the active browser locale through the existing formatter.

## Error and fallback behavior

- Known action with complete translations: show the localized summary.
- Unknown action or missing catalogue entry: show **Unknown audit action** plus the raw action code.
- Missing before/after payload: show the translated no-summary message and retain the available technical payload.
- Unsupported nested change: omit it from the human summary but retain it in sanitized technical JSON.
- No new network request or database fallback is introduced.

## Testing strategy

The public seam is the rendered Audit Log tab as experienced by an administrator.

- A known `kyc.approve` row renders the localized business summary and keeps `kyc.approve` visible.
- Expanding that row renders `Pending → Approved` in the key-change summary.
- Technical JSON is collapsed initially and becomes visible through the disclosure control.
- An unknown action renders **Unknown audit action** and its untouched raw code.
- Sanitized sensitive fields never appear in either summary or technical details.
- Contract coverage verifies every catalogue entry resolves in English, Malay, and Simplified Chinese.
- Existing read-only, seven-column, filtering, pagination, focus, and target-navigation contracts continue to pass.

## Scope boundaries

### In scope

- Human-readable action summaries.
- Human-readable primitive before/after changes.
- Collapsible sanitized JSON evidence.
- Exact tri-lingual action and field vocabulary.
- Focused component and translation-contract tests.

### Out of scope

- Resolving actor UUIDs to names, emails, or avatars.
- Changing audit data already stored in Supabase.
- Adding audit actions, retention rules, exports, signatures, hashing, or tamper-evidence mechanisms.
- Changing audit filters, pagination, authorization, API enrichment, or KYC event correlation.
- Formatting nested objects or arrays as domain-specific summaries.
- Redesigning other admin tables or domain-specific timelines.

## Dependencies, database changes, and risks

- New dependencies: none.
- Database changes: none.
- Migration changes: none.
- Primary maintenance risk: a newly introduced audit action can reach production before its catalogue translation is added. The explicit unknown state prevents misinformation, while catalogue/locale tests make missing known coverage visible during development.
- Primary UX risk: excessive change rows can make an expanded event noisy. The first version summarizes only changed primitive sanitized fields and leaves complex structures in technical JSON.
- Primary privacy risk: accidentally formatting raw data. The implementation must accept only the sanitized `AuditRecord.before` and `AuditRecord.after` values already returned by the current API.

## Acceptance criteria

- An administrator can identify the meaning of a known action without expanding the row.
- The KYC example reads as an approval and clearly shows `Pending → Approved` when expanded.
- The raw action code and sanitized JSON remain available for investigation.
- Unknown actions are explicit rather than guessed.
- All supported locales provide the same semantic coverage.
- No database, API, authorization, or sensitive-data boundary changes are introduced.
